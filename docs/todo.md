- [x] **Post-launch bugfix**: the first real live click-through surfaced a real bug — asking a question showed the "Searching filings for AAPL" status and then stalled forever with no error, no answer. Root-caused to two compounding gaps: (1) `api/chat.py`'s `generate()` had `except Exception: db.rollback(); raise` — any failure after streaming started died silently instead of producing a visible `error` SSE event, and there was zero server-side exception logging anywhere in the turn; (2) no Mistral SDK call in the retrieval chain (`DocumentRetriever._embed_query`, `retrieval/keywords.py::extract_keywords`) passed an explicit `timeout_ms`, so a slow/stuck call had no bound. Fixed: both calls now pass explicit timeouts (`mistral_request_timeout_ms=15000`, `retrieval_keyword_extraction_timeout_ms=6000`, both in `config.py`); `generate()`'s catch-all now logs (`logger.exception`) and yields a clean `format_error(...)` instead of re-raising; added an overall per-turn watchdog (`chat_turn_timeout_seconds=60`) that cancels the task and surfaces a timeout error if a turn runs unreasonably long. `backend/tests/test_chat_api.py` gained a case asserting an unexpected exception from the turn runner produces `event: error` (not a dropped/broken stream) with no partial assistant message persisted.
- [x] **Post-launch latency + typing-effect pass**: the user asked why answers were slow and wanted a typing effect instead of the answer popping out at once. Two real, independent causes fixed: (1) `DocumentRetriever.search()` (`backend/app/retrieval/retriever.py`) was making its two Mistral calls per search (embedding + keyword extraction) sequentially despite them being independent — now run concurrently via `concurrent.futures.ThreadPoolExecutor`, cutting that portion of latency from the sum of both calls to the max of the two. - [x] **Post-launch "no response until Stop" bugfix**: user reported asking a question produced no visible answer, and clicking Stop made it "pop up." Root cause confirmed by reading the AI SDK source directly: `onFinish` fires on **any** stream termination, including a user-initiated abort (not just success), and `ChatSession.tsx`'s `onFinish` unconditionally refetches and displays whatever's persisted — so an abort just happened to reveal an answer the backend had already finished computing in the background (since nothing was cancelling it server-side). This is the same multi-round-trip latency already diagnosed, just manifesting as "looks dead, Stop reveals it" instead of "looks dead, reload reveals it."
  - First fix attempt: `finally: if not task.done(): task.cancel()` wrapping `generate()`, relying on Starlette's generator cleanup when a disconnect breaks a `send()`. **Confirmed insufficient by the user re-testing live** — clicking Stop still revealed the answer. Root-caused: Starlette only discovers a broken connection the *next time it tries to send a chunk*, and our generator can go up to `chat_heartbeat_interval_seconds` between yields — so the abandoned generator's cleanup depended on CPython's refcounting GC timing after an unhandled exception, which isn't a reliable/prompt trigger in the real request path (only in an isolated test that calls `.aclose()` explicitly, which is why the first version's test passed while the live behavior didn't).
  - Real fix: an explicit `await request.is_disconnected()` poll (FastAPI's `Request`, backed by Starlette's non-blocking ASGI receive-channel check) added directly inside `generate()`'s existing polling loop — deterministic, no reliance on implicit cleanup. `backend/tests/test_chat_api.py`'s regression test was rewritten to call `stream_chat` directly with a fake `Request` (`is_disconnected()` reporting connected-then-disconnected) rather than depending on generator GC, since Starlette's `TestClient` cannot simulate a genuine mid-stream disconnect at all (confirmed by reading `starlette/testclient.py` — its fake ASGI `receive()` only ever reports `http.disconnect` *after* the response has already fully completed). `uv run pytest -m "not integration"` 60/60 passing.
  - **User still saw the same symptom after this fix.** Investigated live by restarting the backend under direct log observation (`uv run uvicorn ... > backend_watch.log`) — twice found a *stale backend process still bound to port 8000* (leftover from earlier debugging sessions in this same conversation), meaning the user had been testing against old code the whole time and none of the fixes above had actually been in effect. Cleared all stray `python.exe` processes and confirmed a clean bind before retesting.
  - **Bigger finding while adding diagnostics**: `backend/app/main.py` had **no logging configuration at all** — Python's root logger defaults to WARNING with no console handler, so every `logger.info(...)` call added across this entire debugging session (turn timing, disconnect/heartbeat tracing) was being silently dropped and was never actually visible in the terminal, which likely explains why the user couldn't confirm any of this from their side. Fixed with `logging.basicConfig(level=logging.INFO, format=...)` in `main.py`. Also added detailed timestamped tracing so the pipeline is now directly observable in the terminal: `app/assistant/agent.py` logs every tool call's arguments, duration, and result count; `app/chat/orchestrator.py` logs total turn duration and unique-chunks-retrieved count; `app/api/chat.py` logs when a stream request is received, when each heartbeat fires (with elapsed seconds), and total stream duration to `done`.
  - **Resolution**: with a genuinely fresh backend + visible logging, the pipeline actually worked — the user got a real, complete, well-formatted answer. The remaining issue was unrelated to the pipeline: `frontend/src/components/chat/MessageList.tsx` rendered assistant text in a plain `<span>`, so the model's markdown output (`###` headings, `**bold**`, `- ` bullets, `[text](url)` links) showed up as literal unrendered syntax instead of formatted text. Fixed by adding `react-markdown` + `remark-gfm` (`frontend/src/components/chat/Markdown.tsx`, custom `components` mapping styled onto the existing design tokens rather than pulling in `@tailwindcss/typography`) and rendering assistant message parts through it; user messages stay plain text. `pnpm tsc --noEmit`, `pnpm lint`, `pnpm build` all clean.
